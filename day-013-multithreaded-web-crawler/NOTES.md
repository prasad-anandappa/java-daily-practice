# Day 013 — Multithreaded Web Crawler

**Problem.** Given a start URL and an `HtmlParser` that returns the links on a page, crawl every page reachable from the start, following only links with the same hostname as the start URL, fetching each page exactly once — and fetch in parallel. (LeetCode 1242, Hard.)

**Approach.** A `ForkJoinPool` of `RecursiveAction`s over a visited set backed by `ConcurrentHashMap.newKeySet()`. The whole correctness argument is one line: a link is claimed with the atomic `visited.add(url)` *before* its task is forked, so when thirty pages link to the same target simultaneously, exactly one racer's `add` returns `true`, exactly one task is forked, and the page is fetched exactly once — no locks, no check-then-act race. Hostname filtering happens before the claim, so foreign-host URLs never enter the set. Each task forks its newly claimed children and joins them; `pool.invoke` returns only when the transitive crawl is complete. `main` cross-checks against an independent oracle — a plain single-threaded BFS computing the reachable same-host set — over 100 random graphs with cycles, duplicate edges and cross-host links, and additionally records per-URL fetch counts and the set of fetching threads in the fake parser, so exactly-once and real parallelism are asserted, not assumed.

**Complexity.** Each reachable page is fetched once and each of its links examined once: O(V + E) total work for V reachable pages and E links among them, spread across the pool's threads. Space O(V) for the visited set plus O(E) transient child-task references. Wall-clock time depends on fetch latency and graph shape — wide graphs parallelise, a pure chain cannot (each page reveals only the next).

**Takeaways.**
- "Fetch each page exactly once, in parallel" is an atomic-claim problem, not a locking problem: test-and-set on a concurrent set at discovery time beats synchronised check-then-act at fetch time, which races.
- A fixed `ExecutorService` crawler whose tasks submit children and block on their futures can thread-starvation-deadlock: every pool thread ends up a parent waiting for children that can never be scheduled. ForkJoin's work stealing — a thread blocked in `join()` runs other pending tasks — removes that failure mode, which is why it fits recursive submit-and-wait workloads.
- Parallel code needs oracles for its *concurrency* claims, not just its output: fetch-count maps catch duplicate work that a correct-looking result set hides, and the thread-name set catches a "parallel" crawler that secretly ran on one thread.
