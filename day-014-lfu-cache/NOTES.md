# Day 014 — LFU Cache

**Problem.** Design a cache of a fixed capacity where `get` and `put` both run in O(1) average time. When a new key is inserted into a full cache, evict the least frequently used key; if several keys tie for the lowest frequency, evict the least recently used among them. `get` on a missing key returns -1, and both a successful `get` and a `put` to an existing key count as a use. (LeetCode 460, Hard.)

**Approach.** Two hash maps and a hand-rolled doubly linked list per frequency — the same ingredients `LinkedHashMap` hides. `keyMap` maps key → node; `freqMap` maps frequency → a list of the nodes at that frequency, ordered least-recently touched at the head to most-recently at the tail (sentinel nodes at both ends, so detach and append are pure pointer surgery with no null cases). Touching a key removes its node from its old list in O(1) and appends it to the tail of the next frequency's list. A running `minFreq` names the only bucket eviction ever inspects, so eviction is just popping that list's head — no scan for the minimum. When the minimum list empties because its last node was promoted, `minFreq` increments (sound: that node itself landed at `minFreq + 1`, and nothing can sit between); a brand-new key resets `minFreq` to 1. `main` cross-checks against an independent oracle — a naive implementation that scans every entry for the lowest frequency and oldest touch on each eviction — over 200 randomised trials of 500 operations each at capacities 0–5.

**Complexity.** O(1) average time for both `get` and `put`: every step is a hash lookup or a constant number of pointer updates. O(capacity) space for the nodes, plus one list object per distinct frequency present (at most O(√operations) distinct frequencies in the worst case, bounded by the number of touches of the hottest key, and in practice far below capacity).

**Takeaways.**
- LFU's O(1) trick is maintaining the answer incrementally: `minFreq` is never searched for, it is updated at the two moments it can change — a promotion that empties the minimum bucket, and an insertion that creates a frequency-1 key.
- One ordering structure is not enough: frequency is the primary eviction key and recency is the tie-breaker, so the design nests an LRU list *inside* each frequency bucket rather than keeping a single global list.
- Building the list by hand exposes what collections give for free — sentinels turn four edge cases (empty, head, tail, single element) into one code path, which is exactly why `LinkedHashMap` and `LinkedList` use the same device internally.
